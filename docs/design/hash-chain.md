# Hash Chain Design (FR-4.5, FR-5.4)

## Formula
```
entry_hash = SHA-256(prev_hash | transaction_id | account_id | direction | amount | currency | timestamp | entry_id)
```

## Encoding rules
- Fields are joined with a single `|` character, no spaces.
- The joined string is encoded as UTF-8 before hashing.
- `amount` is the plain integer in minor units (for example `500`).
- `timestamp` is the exact `created_at` string stored in the row (ISO 8601 UTC). The stored string is hashed, never a re-formatted value.
- `entry_id` is the plain integer (for example `1`).
- The output is lowercase hexadecimal, 64 characters.

## Genesis
The first entry has `prev_hash` = 64 zero characters (`"0" * 64`). Every later entry's `prev_hash` is the `entry_hash` of the entry with the highest `entry_id` at that moment.

## How entry_id is chosen before the insert
`entry_hash` includes `entry_id`, so the id must be known before hashing. Inside `BEGIN IMMEDIATE` no other writer can insert, so the writer:
1. Reads the last row: `SELECT entry_id, entry_hash FROM ledger_entries ORDER BY entry_id DESC LIMIT 1`.
2. Sets `entry_id = last_entry_id + 1` (or 1 if the table is empty) and `prev_hash = last_entry_hash` (or the genesis hash).
3. Computes `entry_hash` with the formula above.
4. Inserts the row with that explicit `entry_id`.
5. Repeats for each further entry of the same transaction, each chaining to the one just inserted.

If the transaction rolls back, no row was written, so no ids are consumed and the chain has no gaps.

## Verification (reconciliation)
1. Read all entries ordered by `entry_id` ascending.
2. For each entry, check that `prev_hash` equals the previous entry's `entry_hash` (genesis for the first).
3. Recompute `entry_hash` from the stored fields and compare.
4. Report the first `entry_id` that fails either check, and set `overall_status` to FAIL.

## Worked example
Generated by `scripts/hash_example.py`:

| entry_id | prev_hash | transaction | account | direction | amount | currency | timestamp |
|---|---|---|---|---|---|---|---|
| 1 | 64 zeros | T-1 | ACC-A | DEBIT | 500 | INR | 2026-11-20T10:00:00Z |
| 2 | hash of entry 1 | T-1 | ACC-B | CREDIT | 500 | INR | 2026-11-20T10:00:00Z |

```
entry 1: 4f073952144f327012741c8a0eaf65f29a48b57dbb9564a2b005fc5a5cb3bb2e
entry 2: ee55968744cb98393529f6f6163fcc25df498d2b06e6f996f21b0f6f5d93d4ad
```

Changing any field of entry 1 changes its hash, which no longer matches `prev_hash` in entry 2, so the tamper is detected.
